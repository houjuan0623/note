# connect\&bind\&listen\&accept

## bind

一个新创建的套接字虽然存在于某个地址族（如 `AF_INET`）中，但它是匿名的，没有被分配任何具体的地址。

`bind()` 系统调用的作用就是解决这个问题，它将一个本地地址（IP 和端口号）与一个套接字描述符关联起来 。对于服务器而言，这是在接受连接之前必须执行的关键步骤 。

当内核收到一个 `bind()` 调用时，它会执行一系列严格的验证：

* 描述符有效性：检查 `sockfd` 是否是一个指向套接字的有效文件描述符 (`EBADF`, `ENOTSOCK`) 。  &#x20;
* 地址有效性：确保提供的地址对于套接字的地址族是有效的，并且该套接字尚未被绑定 (`EINVAL`) 。  &#x20;
* 权限检查：验证进程是否拥有绑定到所请求端口的权限。例如，在类 Unix 系统中，绑定到 1024 以下的端口通常需要超级用户权限 (`EACCES`) 。  &#x20;
* 地址可用性：检查该 IP 地址和端口号的组合是否已被其他套接字占用 (`EADDRINUSE`)。这是 `bind()` 调用中最常见的错误 。

如果所有检查都通过，内核会将本地地址和端口信息更新到内部的 `struct sock` 结构体中。这一操作将抽象的套接字对象锚定到网络上的一个具体坐标，使其能够被客户端发现和连接。

## listen

设置套接字的属性为被动监听套接字。

从用户进程的角度看，`listen()` 是一个非常简单的、非阻塞的操作 。它的唯一目的，是将一个已绑定的套接字标记为“被动”套接字，表明它愿意接受传入的连接请求 。

这个调用将套接字的角色从一个可以发起连接（通过 `connect()`）的主动实体，转变为一个只能接收连接的被动实体。它是调用 `accept()` 的先决条件 。

在 `listen()` 调用期间，内核执行的最重要的动作是为这个监听套接字分配和初始化两个用于管理传入连接请求的关键队列 。

### 监听套接字的两个队列

现代 Linux 内核使用两个独立的队列来管理监听套接字的传入 TCP 连接 。这种双队列系统取代了早期单一队列的模型，为处理连接建立过程提供了更精细的控制。

[可以提前参考TCP相关的文章。](tcp.md)

**SYN 队列（未完成连接队列）：**

* 目的：此队列（通常以哈希表实现）用于存储已完成 TCP 三次握手第二步的连接请求。当服务器收到客户端的 SYN 包时，它会回复一个 SYN-ACK 包，并在 SYN 队列中为此连接请求创建一个轻量级的数据结构 (`struct inet_request_sock`) 。此时，连接处于`SYN_RECV` 状态。
* 大小：该队列的大小由一个全局内核参数 `/proc/sys/net/ipv4/tcp_max_syn_backlog` 控制 。

**Accept 队列（已完成连接队列）：**

* 目的：此队列用于存放已经完成完整三次握手、处于 `ESTABLISHED` 状态的连接。这些连接正在等待应用程序通过 `accept()` 系统调用来取走 。当服务器收到来自客户端的最终 ACK 包时，内核会创建一个完整的套接字结构 (`struct inet_sock`)，将连接从 SYN 队列移至 Accept 队列，此时服务器端的连接状态变为 `ESTABLISHED` 。  &#x20;
* 大小：该队列的大小由传递给 `listen()` 系统调用的 `backlog` 参数直接控制 。然而，这个值会被全局内核参数`/proc/sys/net/core/somaxconn` 静默地限制在其上限之内 。

> 从单一队列到双队列的演进，是内核网络栈设计思想成熟的体现。
>
> 早期的 BSD 模型使用单一队列，`backlog` 参数控制着未完成 (`SYN_RECV`) 和已完成 (`ESTABLISHED`) 连接的总和 。这导致了应用性能和网络性能的紧密耦合：
>
> * 一个处理缓慢的应用程序（不及时调用`accept()`）可能导致队列被 `ESTABLISHED` 状态的连接占满，从而无法接受新的连接请求；
> * 反之，一个高延迟的网络可能导致队列被 `SYN_RECV` 状态的连接占满，使得一个处理迅速的应用程序也无事可做 。
>
> Linux 的双队列模型则将这两个问题解耦 。应用程序开发者根据其处理`accept()` 的速度来调整 `backlog` 参数，而系统管理员则根据网络状况（如 RTT 和预期的连接速率）来调整 `tcp_max_syn_backlog` 。
>
> 这种关注点分离的设计，允许对系统进行更精确、独立的调优，因为它深刻认识到高性能服务器的瓶颈可能来自**应用层**，也可能来自**网络层**。
>
> * Accept 队列溢出：如果应用程序调用 `accept()` 的速度不够快，Accept 队列将会被填满。当队列满时，内核的行为由 `/proc/sys/net/ipv4/tcp_abort_on_overflow` 参数决定。如果设置为 0（默认值），内核会简单地丢弃客户端发来的最终 ACK 包。这会导致服务器端的连接停留在 SYN 队列中，而客户端却认为连接已建立，最终造成半开连接和客户端超时 。如果设置为 1，内核会发送一个 RST 包，使客户端连接立即失败 。一个满的 Accept 队列也会导致内核开始丢弃新传入的 SYN 包 。  &#x20;
> * SYN 队列溢出与 SYN 洪水攻击：SYN 队列是 SYN 洪水 (SYN Flood) DDoS 攻击的主要目标。攻击者发送大量 SYN 包（通常来自伪造的 IP 地址），但从不发送最终的 ACK。这会用半开连接填满服务器的 SYN 队列，消耗服务器内存，并阻止合法用户建立连接 。  &#x20;
> * 内核防御：SYN Cookies：为了对抗 SYN 洪水攻击，内核采用了一种名为 SYN Cookies 的机制，由 `/proc/sys/net/ipv4/tcp_syncookies` 控制 。当 SYN 队列已满且 SYN Cookies 被启用时，服务器不会在 SYN 队列中创建条目。相反，它会将连接的必要信息（如 MSS、时间戳等）编码到一个经过特殊计算的序列号中，并将其作为 SYN-ACK 包的初始序列号发送出去。合法的客户端会回复一个 ACK，其确认号为 `序列号 + 1`。服务器收到此 ACK 后，可以通过密码学方法验证其有效性，并从中解码出连接信息，然后直接将连接放入 Accept 队列，整个过程完全无需在 SYN 队列中存储任何状态 。

## connect：主动建立连接

调用connect传递套接字地址结构的方向是：用户进程->内核进程

从用户进程的角度来看，`connect()` 是发起与远程服务器连接的系统调用 。应用程序提供套接字描述符和服务器的地址，之后的一切都交由内核处理。

如果客户端套接字没有被显式地绑定到一个本地地址和端口，内核会在 `connect()` 调用期间，自动从 `/proc/sys/net/ipv4/ip_local_port_range` 指定的范围内为其分配一个临时端口 。
