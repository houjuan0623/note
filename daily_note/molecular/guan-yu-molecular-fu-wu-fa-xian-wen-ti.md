# 关于 molecular 服务发现问题

## TCP & UDP

利用molecular提供利用TCP+UDP进行服务发现的机制，具体流程如下所述：

1. 执行molecularjs，初始化微服务框架。
2. 启动TCP server & UDP server。
3.  新节点启动，UDP server 定期(setInterval)**将自身的节点信息传播给其他节点**。这里使用 UDP 组播消息。

    > 其他节点监听该组播地址，接收到消息后，会尝试与新节点建立连接。
    >
    > 注意：
    >
    > * 这种方式简单高效，但仅限于局域网内，且 UDP 协议本身不可靠。
4.  TCP server 采用Gossip协议**确保信息可靠传播。**&#x5B9A;期(setInterval)查询nodes信息，节点之间会建立 TCP 连接，使用 Gossip 协议进行信息交换，确保信息能够可靠地传播到所有节点。除了节点地址和端口，Gossip 协议还可以用于同步节点状态、CPU 使用率、服务信息等更详细信息。

    > * 节点之间建立 TCP 连接后，会定期交换节点信息，包括节点 ID、地址、端口、服务列表等。
    > * 每个节点维护一个本地节点列表，并根据收到的信息更新列表。
    > * 这种方式可以跨网络工作，并且具有一定的容错性，但信息传播速度相对较慢。

### 为什么不采用UDP组播进行信息交换？

**UDP 组播的优点：**

* **简单高效：** UDP 是一种无连接协议，发送消息不需要建立连接，效率很高。
* **自动发现：** 新节点加入集群时，可以通过监听组播地址自动发现其他节点。

**UDP 组播的缺点：**

* **不可靠：** UDP 是一种不可靠的协议，消息可能会丢失，而且无法保证所有节点都能收到消息。
* **安全性低：** UDP 广播的信息可以被任何监听该端口的设备接收到，安全性较低。
* **网络限制：** UDP 广播通常只在局域网内有效，如果节点分布在不同的网络环境中，则无法使用 UDP 广播进行节点发现。

**Gossip 协议的优点：**

* **容错性高：** 即使部分节点不可达，Gossip 协议也能保证信息最终传播到所有节点。
* **可扩展性强：** Gossip 协议适用于大规模集群，节点数量增加不会对性能造成太大影响。
* **信息同步：** Gossip 协议不仅可以用于节点发现，还可以用于同步节点状态、服务信息等。

**Gossip 协议的缺点：**

* **信息传播延迟：** Gossip 协议的信息传播速度相对较慢，需要经过多轮传播才能达到所有节点。
* **实现复杂：** Gossip 协议的实现相对复杂，需要考虑信息冗余、冲突解决等问题。

### molecular使用了什么机制监听连接？为什么不使用心跳机制监听链接？

Moleculer 没有强制使用心跳机制来检测远程节点的健康性，而是采用了更灵活的方式，根据不同的 Transporter 和服务发现机制来实现。

**为什么不总是使用心跳？**

* **网络开销:** 心跳包会增加网络流量，尤其是在大规模集群中，每个节点都需要定期发送心跳，会造成不必要的网络负担。
* **配置复杂:** 需要配置心跳间隔、超时时间等参数，增加了配置的复杂度。
* **并非所有场景都适用:** 有些 Transporter 或服务发现机制本身就提供了节点状态监控的功能，例如 TCP Transporter 的连接状态监控和 etcd 的租约机制，这种情况下，心跳机制就显得多余。

**Moleculer 中常用的节点健康检测机制:**

1. **TCP Transporter:**
   * **连接状态监控:** `TcpReader` 和 `TcpWriter` 会监听 TCP 连接的 `close` 和 `error` 事件，一旦连接断开或发生错误，就会将对应节点标记为离线。
   * **Gossip 类机制:** 节点之间会定期交换节点信息，包括节点状态、CPU 使用率等。如果一个节点长时间没有更新信息，其他节点会将其视为不健康。
2. **Etcd3Discoverer:**
   * **租约机制 (Lease):** `sendHeartbeat` 函数会为心跳信息创建一个租约，租约有一定的有效期。如果节点因为故障等原因无法续租，则心跳信息会自动过期，其他节点会将其视为离线。
3. **其他 Transporter (例如 NATS、MQTT):**
   * **心跳机制:** 这些 Transporter 通常会使用心跳机制来表明节点的活跃状态。如果一段时间内没有收到心跳包，则认为节点不可用。
